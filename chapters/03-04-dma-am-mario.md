# 3.4 DMA设计及其在AM图形应用中的使用

图像显示和加速器计算都需要在存储器与外设之间传输连续数据。若由CPU使用普通加载、存储指令逐字搬运，处理器每传输一个数据字都要完成取指、译码、地址计算和总线访问，搬运期间难以执行游戏逻辑、设备管理等其他任务。本设计在SoC中加入DMA（Direct Memory Access）控制器，将连续数据传输从CPU指令流中分离出来。本节按照“DMA基本原理—硬件数据通路—SoC总线集成—软件驱动—AM移植—FCEUX应用”的顺序展开，从底层传输机制逐步说明其在《超级马里奥》运行环境中的作用。

## 3.4.1 DMA基本原理

CPU执行内存复制时，需要循环读取源地址、写入目的地址并更新循环变量。以32位总线搬运长度为$L$字节的数据，理想情况下也至少包含约$L/4$次读操作和$L/4$次写操作，实际执行还会受到流水线、缓存和总线等待影响。DMA把这一循环固化为硬件状态机。CPU只需给出源地址、目的地址和传输长度，DMA取得总线访问权后自动产生地址、组织突发、接收读数据并发起写事务，完成后再通过状态位或完成信号通知CPU。

一笔DMA任务可以分为配置、传输和完成三个阶段。配置阶段由CPU写入描述符，描述符至少包含起始地址和字节长度；传输阶段由DMA按照总线握手状态推进读写地址，目标设备暂时无法接收数据时通过反压暂停，不会依靠固定延时猜测事务是否结束；完成阶段在末尾数据拍被目标端接受后产生状态。CPU只参与任务边界，不参与每个数据拍，因此可以把处理器周期留给图像处理控制、游戏模拟和其他软件任务。

本设计的DMA连接32位AXI总线，一个完整数据拍最多携带4字节。控制器将较长任务拆分为多个AXI突发，当前最大突发长度为16拍，即单次突发最多传输64字节。连续地址使用突发事务后，地址通道不必为每个数据字重复握手，能够降低连续帧缓冲搬运中的控制开销。末尾数据拍由`last`信号标记，不足4字节的尾部数据由字节有效信号指示，保证任意字节长度的任务仍能正确结束。

## 3.4.2 DMA硬件结构与传输过程

顶层实例化的`axi_dma`由读描述符接口、AXI读引擎、AXI-Stream中间通路、AXI写引擎和写描述符接口组成。读描述符给出源地址与长度，读引擎通过AXI读地址通道发起突发，并从读数据通道接收返回值；写描述符给出目的地址与长度，写引擎把AXI-Stream中的数据转换成AXI写地址、写数据和写响应事务。当前顶层把DMA读流直接回接到DMA写流，因此同一控制器可以完成存储器到存储器，或存储器到存储器映射外设数据口的搬运。

```text
CPU写配置寄存器
        │ 源地址、目的地址、长度、启动位
        ▼
DMA描述符控制
        │
        ├──► AXI读引擎 ──AR/R──► AXI Crossbar ──► 源设备
        │          │
        │          ▼
        │    AXI-Stream数据
        │    data/keep/valid/ready/last
        │          │
        └──► AXI写引擎 ──AW/W/B─► AXI Crossbar ──► 目的设备
                   │
                   ▼
              完成状态返回
```

图3-3 DMA读写数据通路

AXI读写通道彼此独立。读引擎只有在内部流通路能够继续接收数据时才保持`rready`，写引擎只有在收到有效流数据后才发出写数据。中间的`valid/ready`握手使读侧速度能够跟随写侧：若目的设备拉低ready，写引擎暂停，中间流产生反压，读引擎也停止接收新的返回数据，避免在没有足够缓存时覆盖尚未写出的内容。`tkeep`传递每拍有效字节，`tlast`标识描述符末尾，使读写两侧在字节数和事务边界上保持一致。

DMA在`sys_clk`域工作，地址宽度和数据宽度均为32位，事务ID宽度为4位。它作为系统中的独立AXI发起端接入Crossbar，与CPU和TPU处于同一级。DMA访问共享SRAM时，Crossbar依据地址选择目标端口；若CPU或TPU同时访问同一SRAM端口，仲裁器决定事务先后；若各主设备访问不同目标，则对应事务可以并行推进。DMA由此获得自主访存能力，而不是借用CPU的AXI主接口执行搬运。

## 3.4.3 总线集成与寄存器控制

DMA同时具有控制面和数据面。控制面是位于Crossbar M5窗口的AXI-Lite从接口，物理地址范围为`0x1F30_0000`～`0x1F3F_FFFF`；裸机软件使用非缓存别名`0xBF30_0000`访问该窗口。数据面是DMA的完整AXI主接口，经Crossbar发起实际的读写事务。CPU写配置寄存器只是在控制面提交任务，不会把待搬运数据写入DMA配置窗口。

表3-3 DMA配置寄存器

| 偏移 | 名称 | 有效位 | 访问属性 | 功能 |
|---:|---|---|---|---|
| `0x00` | `READ_ADDR` | `[31:0]` | R/W | AXI读源地址 |
| `0x04` | `READ_LEN` | `[19:0]` | R/W | 读长度，单位为字节 |
| `0x08` | `WRITE_ADDR` | `[31:0]` | R/W | AXI写目的地址 |
| `0x0C` | `WRITE_LEN` | `[19:0]` | R/W | 写长度，单位为字节 |
| `0x10` | `COMMAND` | `[1:0]` | W，读回0 | bit0启动读，bit1启动写 |
| `0x14` | `STATUS` | `[9:0]` | R | ready、busy、done、命令等待及描述符完成状态 |

增强版`dma_config_axil`在`STATUS[0]`和`STATUS[1]`给出读、写描述符ready，`STATUS[2]`表示任务忙，`STATUS[3]`表示任务完成；`[5:4]`表示读写命令仍在等待握手，`[7:6]`表示对应描述符尚未完成，`[9:8]`记录本轮已经收到读写完成状态。写`COMMAND=1`只启动读引擎，写`COMMAND=2`只启动写引擎，写`COMMAND=3`同时启动两侧。顶层还把读写完成状态的或结果送入`confreg_dma_finish`，为后续采用中断代替软件轮询保留了接口。

软件提交内存复制时，先等待读写描述符接口均处于ready状态，再依次写入源地址、读长度、目的地址和写长度。内存屏障保证前述配置以及CPU对源缓冲区的写入已经对总线可见，随后向命令寄存器写入`0x3`。DMA接受描述符后置位busy，读写引擎完成后清除busy并置位done。源地址和目的地址必须使用DMA能够识别的AXI物理地址，而不能把CPU使用的`0xB...`非缓存别名直接交给DMA。

工程中还保留了一个简化版同名`dma_config_axil`，该版本的状态寄存器只返回两个ready位，而`rtl/ip/verilog-axi-master/rtl/dma_config_axil.v`实现了上述完整状态并带有读写完成输入。当前`soc_top.v`的端口连接与增强版一致。综合和仿真源列表应只保留与顶层匹配的实现，否则会出现同名模块重复定义，或软件读取不到busy、done等状态的问题。

## 3.4.4 DMA在视频帧搬运中的应用

NES画面的有效分辨率为256×240。AM显示后端使用8位RGB332像素时，一帧数据量为

$$
L=256\times240\times1=61440\ \text{Byte}.
$$

若CPU按32位逐字复制，一帧需要执行15360次数据读写循环；DMA则只需软件配置一组读写描述符。按16拍、每拍4字节的最大突发计算，完整帧可分解为960个64字节突发。该数量只表示事务分块，不等同于固定执行周期，实际传输时间还取决于SRAM响应、Crossbar仲裁和DVI数据口反压。

AM旧DVI兼容路径在共享SRAM中设置两个影子帧缓冲，AXI基地址从`0x1C40_0000`开始，两页间隔`0x1_0000`字节。CPU使用对应的`0xBC40_0000`非缓存别名绘制当前帧。提交显示时，软件配置DVI窗口，将DMA源地址设置为当前影子帧缓冲，将目的地址设置为DVI数据端口`0x1F10_0014`，读写长度均设为61440字节，再同时启动DMA读写。描述符提交后切换绘制页，显示端读取上一页时CPU可以准备下一页，从而避免同一缓冲区被同时修改和显示。

```text
FCEUX生成第n帧
        │
        ▼
CPU写影子帧缓冲A ──内存屏障──► DMA读取A ──► DVI显示第n帧
        │                         │
        └──切换缓冲区             │
                                  ▼
CPU写影子帧缓冲B             DMA完成/状态返回
```

图3-4 视频双缓冲与DMA协同

当前AM代码通过`AM_USE_NEW_DVI`保留两条显示路径。宏为0时使用上述影子帧缓冲和DMA刷新；宏默认值为1时，软件直接把像素复制到新版DVI的`0xB100_0000`帧缓冲，并未调用DMA。因此，DMA视频搬运是已经写入AM旧DVI后端的兼容方案，而当前默认构建仍采用CPU直写新版帧缓冲。后续若要在新版DVI上发挥DMA作用，需要为新版帧缓冲确认可由DMA访问的物理地址，并把IOE提交路径改为描述符驱动。

## 3.4.5 AM运行环境的LoongArch移植

DMA完成底层数据搬运后，还需要软件抽象层把处理器和外设能力提供给应用。AM（Abstract Machine）把裸机运行环境划分为TRM、IOE、CTE、VME和MPE等接口。本项目新增`loongarch32r-soc`目标，使同一套应用能够通过AM接口调用LA500 SoC的UART、定时器和图形输出，而不在FCEUX源码中直接散布硬件地址。

移植从启动和基本运行环境开始。`start.S`建立复位入口与栈，随后进入`trm.c`的`_trm_init`；TRM遍历C/C++构造函数数组，调用应用`main`，并通过`putch`访问`0xBF00_0000`处的UART。链接脚本给出代码、数据、堆和栈的布局，Makefile使用`loongarch32r-linux-gnusf`交叉工具链生成裸机ELF和二进制镜像。`timer.c`依据SoC计数器实现`AM_TIMER_UPTIME`，为模拟器控制帧节奏提供时间基准。

IOE把图形设备请求映射到DVI与DMA操作。`AM_GPU_CONFIG`向应用报告256×240分辨率和61440字节显存，`AM_GPU_FBDRAW`接收像素块、坐标和同步标志。新版DVI路径把像素写入映射帧缓冲，旧版DVI路径先整理到软件背板和影子页，再在同步请求到达时调用`dvi_dma_flush_shadow`。从应用角度看，两条路径都表现为同一组AM GPU接口，这正是抽象层移植的作用：硬件实现变化集中在`am/src/loongarch/soc/ioe.c`，FCEUX绘图代码无需随总线地址修改。

异常与上下文接口由`trap.S`和`cte.c`提供，VME接口当前返回未启用，表明本系统运行在单地址空间裸机环境中。输入接口仍是当前移植的缺口：`input.c`固定返回`AM_KEY_NONE`，`AM_INPUT_CONFIG`也报告设备不存在。FCEUX README中列出的键位属于上层既定映射，但在补充板级按键扫描或UART键盘驱动之前，当前`loongarch32r-soc`镜像不能据此完成实际按键操作。

## 3.4.6 FCEUX与《超级马里奥》的构建和运行链路

FCEUX位于`sdk/software/examples/loongson_AM/fceux-am`。移植版保留NES的6502处理器、PPU、卡带映射和画面生成逻辑，并把平台相关的计时、绘图和输入替换为AM接口。由于裸机环境没有文件系统，`nes/build-roms.py`将`nes/rom/mario.nes`转换为`nes/gen/mario.c`中的常量数组，ROM数据与模拟器一同链接进镜像。Makefile默认使用`ARCH=loongarch32r-soc`和`mainargs=mario`，同时启用`-O3`、帧跳过和CPU周期计数配置。

完整启动过程从SoC复位开始。LA500从SRAM中的镜像取指，AM完成栈、UART、计时器和IOE初始化后进入FCEUX主函数；FCEUX依据`mainargs`选择Mario ROM，建立NES内存映射并循环执行6502指令；PPU产生一帧256×240索引像素，显示驱动将其转换为RGB332数据并通过`AM_GPU_FBDRAW`提交；AM后端再选择新版DVI直写路径或旧版DVI的DMA路径。由此形成“裸机启动—AM设备抽象—FCEUX模拟—帧缓冲提交—DVI输出”的逐层软件栈。

```text
《超级马里奥》ROM
        │ ROM转C数组并链接
        ▼
FCEUX：6502、PPU、卡带与游戏逻辑
        │ AM_TIMER / AM_GPU / AM_INPUT
        ▼
LoongArch AM运行时
        │ MMIO寄存器、帧缓冲、DMA描述符
        ▼
LA500 + AXI Crossbar + DMA + DVI
        │
        ▼
显示画面与输入反馈
```

图3-5 从应用到硬件的运行层次

构建命令如下：

```bash
cd sdk/software/examples/loongson_AM
export PATH="$PWD/../../../toolchains/loongson-gnu-toolchain-8.3-x86_64-loongarch32r-linux-gnusf-v2.0/bin:$PATH"
make -C fceux-am image ARCH=loongarch32r-soc mainargs=mario
```

构建过程依次生成AM与klib静态库、FCEUX ELF、裸机二进制以及用于SRAM初始化的`axi_ram.mif`。仓库中已有`fceux-loongarch32r-soc.elf`、`.bin`和`mario.bin`等产物，能够证明软件已经完成交叉编译和镜像打包；这些文件本身不能替代运行结果。竞赛验收时还需要记录串口启动日志、DVI画面、连续帧输出和按键响应，才能说明应用链路已经闭合。

## 3.4.7 验证方法与现存问题

DMA模块级验证应在AXI-Lite端依次写入地址、长度和命令，检查寄存器锁存值以及描述符`valid/ready`只握手一次；数据侧使用已知源数组，比较目的区每个字节，并覆盖非4字节对齐的尾部、跨多个16拍突发的长传输和目的端随机反压。状态检查需要确认启动后busy置位、读写完成后done置位、下一次启动清除旧done，同时核对`confreg_dma_finish`是否只在有效完成事件到达时触发。

系统级验证应把DMA与AM显示路径联合起来。旧DVI模式下连续生成两帧不同图案，检查两个影子缓冲交替使用、源地址每帧切换、61440字节完整送达DVI数据口，并比较DMA工作期间CPU执行计数是否继续增加。新版DVI模式下需要单独说明当前为CPU直写，不能把画面输出归因于DMA。若后续把新版帧缓冲接入DMA，还应重新验证地址别名、缓存一致性和显示扫描期间的撕裂问题。

AM与FCEUX验证分为构建、启动、显示和交互四层。当前仓库已经具备ROM转换、交叉编译和镜像生成链路，图形后端也能够提交帧缓冲；输入后端仍固定返回无按键，顶层视频链路和具体板级画面也需要实测证据。因此现阶段可以表述为“完成AM运行时与FCEUX/Mario镜像移植，并建立DMA显示兼容路径”，不宜直接表述为“已经完成可交互的超级马里奥实机运行”。补齐输入驱动、统一DMA配置模块并取得上板日志和画面后，才能形成完整的竞赛验收结论。
